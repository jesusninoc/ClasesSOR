# Fundamentos de los sistemas operativos en red

## 1.1. Características y modelos de red

### Qué es un SO en red
- Sistema operativo pensado para funcionar como servidor.
- Proporciona servicios y recursos a los clientes.
- Gestión centralizada de:
  - usuarios
  - archivos
  - impresoras
  - servicios
  - seguridad
- Diferencias con un SO monopuesto:
  - estabilidad
  - muchos usuarios simultáneos
  - seguridad
  - prestación de servicios
  - puede funcionar sin interfaz gráfica
- Ejemplos: Windows Server y Linux Server.

### Modelos de red

**Cliente/servidor**
- Uno o varios servidores centralizados.
- Los clientes utilizan los servicios y recursos.
- Gestión centralizada.
- Control, seguridad y escalabilidad.
- Habitual en empresas y organizaciones.

**P2P / grupo de trabajo**
- Todos los equipos son equivalentes.
- Comparten recursos directamente.
- No existe servidor central.
- Sencillo, pero limitado.
- Adecuado para redes domésticas o muy pequeñas.

> **Remarcar:** diferencia entre un SO de servidor y un SO de escritorio.

## 1.3. Estudio de compatibilidad y modos de instalación

### Compatibilidad

Comprobar:

- **CPU:** 64 bits y virtualización si procede.
- **RAM:** el mínimo permite arrancar; hay que dimensionar según el servicio.
- **Almacenamiento:** capacidad, tipo y controladora.
- **Red:** controlador disponible.
- **Firmware:** UEFI o BIOS heredado; Secure Boot.
- **Lista de compatibilidad:** hardware admitido/certificado.

> **Caso típico:** el instalador no encuentra el disco porque falta el controlador de la controladora RAID.

### Modos de instalación

**Instalación limpia**
- Se instala desde cero.
- Adecuada para un servidor nuevo.
- No arrastra problemas anteriores.
- Obliga a reinstalar servicios y restaurar datos.

**Actualización en el sitio**
- Conserva configuración, roles y datos.
- Solo está admitida entre determinadas versiones/ediciones.
- Puede arrastrar problemas de la instalación anterior.
- Requiere copia de seguridad.

**Migración**
- Se instala un servidor nuevo.
- Se trasladan roles, datos y configuración.
- El servidor antiguo puede mantenerse funcionando.
- Es una opción más segura en producción.

**Instalación paralela / laboratorio**
- Se prueba en otra máquina, normalmente virtual.
- Permite validar antes de modificar producción.

### Imagen ISO
- Comprobar la suma de comprobación.
- Evita trabajar con una imagen dañada.

> **Preguntar:** ¿por qué comprobar la ISO si aparentemente se ha descargado correctamente?

## 1.4. Particionado del disco y sistemas de archivos

### ¿Por qué particionar?
- Separar sistema y datos.
- Evitar que los datos o registros llenen el disco del sistema.
- Facilitar la gestión del almacenamiento.

### MBR

- Esquema clásico.
- Asociado a BIOS.
- Hasta cuatro particiones primarias.
- Limitación de discos de más de 2 TB.

### GPT

- Esquema actual.
- Asociado a UEFI (Unified Extensible Firmware Interface).
- Sin las limitaciones prácticas de MBR.
- Mantiene una copia de la tabla al final del disco.
- Es el esquema utilizado actualmente en servidores.

### UEFI + GPT

Aparece la **partición del sistema EFI (Extensible Firmware Interface)**:

- pequeña;
- FAT32;
- contiene los cargadores de arranque;
- no se utiliza para datos normales.

> **Remarcar:** UEFI es el firmware de arranque y GPT es el esquema de particionado.

### Ejemplo de reparto: disco de 240 GB

| Partición | Tamaño |
|---|---:|
| EFI | 0,5 GB |
| Sistema operativo | 60 GB |
| Intercambio/paginación | 8 GB |
| Datos | 160 GB |
| Sin asignar | 11,5 GB |

- Total utilizado: 228,5 GB.
- Reserva sin asignar: 11,5 GB.
- El espacio libre permite futuras ampliaciones.

### Sistemas de archivos

**Windows**
- **NTFS:** sistema y datos; permisos, cifrado, cuotas y registro por diario.
- **ReFS:** orientado a grandes volúmenes y comprobación de integridad.
- **FAT32/exFAT:** compatibles, pero con limitaciones para un servidor.

**Linux**
- **ext4:** habitual en Debian/Ubuntu.
- **XFS:** habitual en la familia Red Hat; adecuado para grandes volúmenes.
- **LVM:** permite gestionar volúmenes lógicos con mayor flexibilidad.

### Linux: comandos importantes

- La ventaja es que parted no requiere entrar en un menú interactivo (fdisk sí, echo -e "g\nn\n\n\n\nw" | sudo fdisk /dev/sdb)

```bash
lsblk -f
sudo parted /dev/sdb mklabel gpt
sudo parted -a opt /dev/sdb mkpart datos ext4 0% 100%
sudo mkfs.ext4 -L DATOS /dev/sdb1
sudo blkid /dev/sdb1
sudo mkdir -p /srv/datos
sudo mount /dev/sdb1 /srv/datos
```

### `/etc/fstab`

- El montaje realizado con `mount` no es permanente.
- Para montar automáticamente al arrancar se utiliza `/etc/fstab`.
- Utilizar el **UUID** en lugar de `/dev/sdb1`.
- `nofail` evita que un problema con el disco impida el arranque.

Ejemplo:

```text
UUID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx /srv/datos ext4 defaults,nofail 0 2
```

### Windows

Proceso conceptual:
1. Inicializar disco en GPT.
2. Crear volumen.
3. Asignar letra o punto de montaje.
4. Formatear.
5. Comprobar tamaño y escritura.

## 1.5. Selección de componentes: roles, características y paquetes

### Idea principal

> **Instalar únicamente lo necesario.**

Ventajas:
- menor consumo de recursos;
- menor superficie de exposición;
- menos componentes que mantener y actualizar.

### Windows Server

**Roles**
- Servicios principales que ofrece el servidor.
- Ejemplos: archivos, impresión, dominio, web.

**Características**
- Funciones de apoyo.
- Ejemplos: herramientas de administración, clientes de protocolos, copias de seguridad.

Comandos:

```powershell
Get-WindowsFeature
Install-WindowsFeature -Name FS-FileServer -IncludeManagementTools
Uninstall-WindowsFeature -Name Print-Services
```

### Linux

- Instalar únicamente los paquetes necesarios.
- Comprobar los servicios.
- Deshabilitar los que no se utilicen.

```bash
sudo apt update
sudo apt install --no-install-recommends openssh-server
systemctl is-enabled ssh
sudo systemctl disable --now cups
```

> **Remarcar:** un servidor no se instala "entero"; se instala el sistema y los servicios necesarios.

## 1.6. Ejemplo resuelto: estudio de compatibilidad y dimensionado

### Situación

Servidor de archivos para:
- 40 usuarios.
- 5 GB por usuario.
- Carpeta común de 60 GB.

Equipo:
- CPU de 64 bits.
- Virtualización activada.
- 16 GB RAM.
- Dos discos.
- Tarjeta de red con controlador.
- UEFI + Secure Boot.

### Cálculo del almacenamiento

```text
40 × 5 GB = 200 GB
200 + 60 = 260 GB
260 × 1,25 = 325 GB
```

Se elige un volumen de **400 GB**.

### Reparto

- Disco 1 → sistema, EFI e intercambio.
- Disco 2 → datos.

### Compatibilidad

| Componente | Resultado |
|---|---|
| CPU 64 bits + virtualización | Cumple |
| 16 GB RAM | Cumple con margen |
| Dos discos | Cumple |
| Tarjeta de red | Cumple |
| UEFI + Secure Boot | Cumple |
| Controladora de disco | Comprobar |

> **Idea clave:** el dimensionado debe justificarse con las necesidades previstas, no hacerse "a ojo".

## 1.7. Actualizar en el sitio o migrar

### ¿Cuándo actualizar?

- La ruta de actualización está admitida.
- El hardware sigue siendo suficiente.
- Se puede detener el servicio durante un tiempo.

### ¿Cuándo migrar?

- El salto de versión no está admitido.
- El hardware se queda corto.
- La configuración actual es problemática.
- El servicio no puede detenerse mucho tiempo.

### Actualización en el sitio: pasos

1. Comprobar la ruta de actualización.
2. Hacer copia de seguridad y comprobar que se puede restaurar.
3. Documentar la configuración actual.
4. Liberar espacio.
5. Avisar de la ventana de mantenimiento.
6. Ejecutar la actualización.
7. Comprobar:
   - arranque;
   - red;
   - servicios;
   - acceso de los clientes.
8. Documentar el resultado.

### Migración: pasos

1. Instalar el servidor nuevo en paralelo.
2. Instalar roles y estructura de carpetas.
3. Copiar los datos conservando permisos.
4. Probar con un grupo reducido de usuarios.
5. Realizar el cambio definitivo.
6. Mantener el servidor antiguo como respaldo durante unos días.

> **REGLA DE ORO:** nunca realizar un cambio en producción sin una vía de vuelta.

La vía de vuelta puede ser:
- copia de seguridad comprobada;
- instantánea;
- servidor antiguo intacto.

# Resumen de la unidad

## Conceptos que deben quedar claros

1. **SO de red:** proporciona servicios y recursos a otros equipos.
2. **Cliente/servidor:** centraliza servicios, recursos y gestión.
3. **Compatibilidad:** comprobar CPU, RAM, almacenamiento, red y firmware.

5. **Particionado:** planificar la distribución del almacenamiento.
6. **Sistemas de archivos:** elegir según sistema y finalidad.
7. **Superficie mínima:** instalar solo lo necesario.

# Instalación del servidor

## 2.1. Planificación e instalación

### Planificar antes de instalar

Definir previamente:

- **Hardware / VM:**
  - CPU.
  - RAM.
  - Disco.
  - En laboratorio, normalmente máquina virtual.
  - En producción, puede existir RAID para aumentar la fiabilidad.

- **Almacenamiento:**
  - Planificar particiones.
  - Separar sistema y datos.
  - Elegir sistema de archivos.

- **Identificación:**
  - Nombre definitivo del servidor.
  - Sin espacios ni acentos.
  - Ejemplo: `SRV-DATOS`.

- **Red:**
  - IP estática.
  - Máscara/prefijo.
  - Puerta de enlace.
  - DNS.

- **Función del servidor:**
  - Archivos.
  - Dominio.
  - Servicios de red.
  - Otros servicios.

> **Remarcar:** primero se decide qué servidor necesitamos y cómo debe quedar; después se instala.

### Windows Server

Proceso general:

1. Arrancar desde el medio de instalación.
2. Elegir edición.
3. Elegir instalación con o sin interfaz gráfica.
4. Seleccionar disco/particiones.
5. Completar la instalación.
6. Configurar contraseña de administrador.
7. Configurar nombre y red.

### Linux Server

- Instalar una distribución:
  - Ubuntu Server.
  - Debian.
  - etc.
- Habitualmente sin entorno gráfico.
- Configurar:
  - usuario;
  - particiones;
  - red.

Comprobación básica (si hay DHCP activo):

```bash
ip address show
ping -c 2 8.8.8.8
```

> **Remarcar:** tanto Windows Server como Linux Server deben practicarse en el laboratorio virtualizado.

> **Idea clave:** saber planificar e instalar un SO de red propietario y otro libre.

## 2.2. Configuración inicial y comprobación

Una instalación terminada **no significa que el servidor esté listo**.

### Configuración inicial

Comprobar y configurar:

- **Red:**
  - IP estática.
  - Puerta de enlace.
  - DNS.

- **Nombre definitivo** del equipo.
- **Actualizaciones de seguridad.**
- Zona horaria.
- Idioma y teclado.
- Contraseña fuerte de administrador.
- Cortafuegos.
- Deshabilitar servicios innecesarios.
- Instalar los roles/servicios necesarios.

En Linux:

```bash
sudo apt update
sudo apt upgrade -y
```

### Comprobación

Verificar:

- El servidor arranca correctamente.
- El sistema es estable.
- Tiene conectividad.
- Resuelve nombres DNS.
- Los clientes pueden alcanzarlo.
- Los servicios instalados responden.

### Documentación

Registrar:

- Configuración del servidor.
- Nombre.
- IP.
- Roles y servicios.
- Cambios realizados.
- Información de acceso de forma segura.

> **Remarcar:** configurar, comprobar y documentar forman parte de la instalación.

> **Pregunta:** ¿qué sentido tiene instalar un servidor si después no comprobamos que los clientes pueden acceder a él?

## 2.3. Automatización de las instalaciones

### ¿Por qué automatizar?

Instalar manualmente:

- válido para uno o pocos servidores;
- lento si hay muchos equipos;
- puede provocar errores humanos.

Tres métodos principales:

### 1. Instalación desatendida

- El instalador recibe las respuestas automáticamente.
- Se define previamente:
  - idioma;
  - particiones;
  - red;
  - nombre;
  - usuarios;
  - componentes.

En Windows:

```text
unattend.xml
```

### 2. Clonado mediante imagen

- Se prepara un equipo modelo.
- Se instala y configura.
- Se captura como imagen.
- Se replica en otros equipos.

> **Remarcar:** no se configura veinte veces lo mismo; se prepara una vez y se replica.

### 3. Instalación por red

El equipo arranca desde la tarjeta de red y obtiene el instalador desde la red.

Intervienen normalmente:

- **DHCP:** proporciona configuración inicial y ayuda a localizar el servidor de arranque.
- **TFTP:** proporciona los archivos iniciales de arranque.
- **Servidor de instalación:** proporciona el resto de archivos.

> **Remarcar:** DHCP, TFTP y servidor de instalación cumplen funciones diferentes.

### Sysprep en Windows

Antes de clonar una instalación Windows:

```cmd
C:\Windows\System32\Sysprep\sysprep.exe /generalize /oobe /shutdown
```

- `generalize`: elimina información específica del equipo.
- `oobe`: prepara el primer arranque.
- `shutdown`: apaga el equipo.

### Laboratorio virtualizado

Una alternativa muy práctica:

- Crear una **plantilla de máquina virtual**.
- Clonar la plantilla.
- Modificar nombre, IP y configuración específica.

> **Pregunta:** ¿qué método utilizarías para instalar 1 servidor? ¿Y 30 servidores iguales?

## 2.4. Fichero de respuestas y comprobación de la instalación automatizada

### ¿Qué contiene un fichero de respuestas?

Información que normalmente preguntaría el instalador:

- Idioma.
- Teclado.
- Zona horaria.
- País.
- Particionado.
- Sistemas de archivos.
- Nombre del equipo.
- Dominio.
- Usuarios.
- Contraseñas iniciales.
- Configuración de red.
- Roles y paquetes.
- Acciones posteriores a la instalación.

### Punto especialmente delicado

**Particionado:**

- Disco utilizado.
- Particiones.
- Tamaños.
- Sistemas de archivos.
- Qué hacer con los datos existentes.

> **PELIGRO:** un error en el fichero puede borrar un disco equivocado.

### Probar antes de producción

La instalación automatizada debe probarse:

1. En una máquina virtual.
2. Con disco vacío.
3. En la red de laboratorio.
4. Comprobando que no solicita intervención.
5. Repitiendo la prueba hasta obtener un resultado correcto.

> **Remarcar:** escribir el fichero es solo la mitad del trabajo; la otra mitad es probarlo.

### Comprobación posterior

Después de una instalación desatendida comprobar:

- Nombre correcto.
- Particionado correcto.
- Sistemas de archivos correctos.
- IP y red correctas.
- No existe una IP duplicada.
- Componentes previstos instalados.
- Componentes innecesarios no instalados.
- Cuentas correctas.
- Cambio obligatorio de contraseña inicial.
- Sistema actualizado.
- Hora sincronizada.

### Versionado

Guardar las versiones del fichero de respuestas:

- Fecha.
- Cambios realizados.
- Motivo del cambio.
- Versión que funcionó.

> **Idea clave:** el fichero de respuestas también es documentación técnica y debe controlarse por versiones.

## 2.5. Preferencias del entorno y actualización del sistema

### Configuración del entorno

Configurar y documentar:

- **Nombre del equipo:**
  - corto;
  - descriptivo;
  - sin espacios ni acentos.

Ejemplo:

```text
SRV-DATOS
```

- **Zona horaria y hora.**
- **Sincronización horaria.**
- Idioma.
- Distribución de teclado.
- Cuenta del administrador.

Linux:

```bash
sudo hostnamectl set-hostname srv-datos
sudo timedatectl set-timezone Europe/Madrid
timedatectl status
sudo localectl set-keymap es
```

Windows:

```powershell
Rename-Computer -NewName SRV-DATOS -Restart
Set-TimeZone -Name "Romance Standard Time"
```

> **Remarcar:** la hora correcta es importante porque afecta a registros, autenticación y diagnóstico.

### Actualización del servidor

Actualizar un servidor requiere planificación.

**Antes:**

- Copia de seguridad comprobada o instantánea.
- Avisar de la ventana de mantenimiento.
- Preferiblemente fuera del horario de servicio.

**Durante:**

- Aplicar actualizaciones.
- Priorizar las de seguridad.
- Registrar los cambios.
- Reiniciar si es necesario.

**Después:**

- Comprobar que arranca.
- Comprobar servicios.
- Revisar registros.
- Documentar el resultado.

**Si falla:**

- Desinstalar la actualización problemática.
- Restaurar la instantánea/copia según el caso.

> **REGLA DE ORO:** la copia de seguridad se hace **antes** de actualizar, no después.

Linux:

```bash
sudo apt update
sudo apt full-upgrade
sudo apt list --upgradable
systemctl list-units --type=service --state=running
```

### Actualizaciones centralizadas

En organizaciones grandes:

- No actualizar servidor por servidor manualmente.
- Utilizar un sistema/repositorio interno.
- Controlar qué actualizaciones se aprueban y cuándo.
- Probar primero en laboratorio.

> **Idea clave:** actualizar no es simplemente pulsar "Actualizar"; en producción es un cambio controlado.

## 2.6. Preferencias del entorno personal del administrador

### Principio general

> **Personalizar para administrar, no para decorar.**

En un servidor evitar:

- Fondos innecesarios.
- Salvapantallas.
- Programas personales.
- Software que no aporta nada a la administración.

Porque:

- consume recursos;
- aumenta la superficie de ataque;
- complica el mantenimiento.

### Cuenta del administrador

Cada técnico debería utilizar:

- Su propia cuenta nominal.
- Sus propios privilegios.
- Identificación individual en los registros.

Evitar compartir permanentemente una cuenta de administrador.

> **Remarcar:** si todos utilizan la misma cuenta, después es difícil saber quién realizó un cambio.

### Entorno de línea de comandos

En Linux, se puede personalizar `~/.bashrc`:

```bash
alias ll='ls -lh --color=auto'
export PS1='\u@\h:\w\$ '
source ~/.bashrc
```

El indicador puede mostrar:

```text
usuario@servidor:ruta
```

Esto ayuda a evitar trabajar accidentalmente sobre el servidor equivocado.

### Administración remota

Preparar:

- Herramientas de administración remota.
- Conexión desde el equipo del técnico.
- Variables de entorno y rutas necesarias.
- Configuración regional y teclado.

> **Consejo práctico:** en un laboratorio con varios servidores, que el nombre del equipo aparezca siempre en la consola evita errores.

## 2.7. Ejemplo resuelto: instalar y documentar los servidores

### Situación

Hay que instalar:

- Windows Server.
- Linux Server.

Ambos se utilizarán para las siguientes unidades.

### Estrategia

1. Crear las máquinas virtuales.
2. Asignar recursos.
3. Instalar Windows Server.
4. Instalar Linux Server.
5. Configurar:
   - IP estática;
   - nombre;
   - actualizaciones;
   - contraseña de administrador;
   - cortafuegos.
6. Comprobar:
   - arranque;
   - red;
   - DNS;
   - acceso desde los clientes.
7. Documentar la configuración.

### Resultado

Los dos servidores quedan:

- instalados;
- configurados;
- actualizados;
- comprobados;
- documentados.

Y preparados para instalar posteriormente:

- usuarios;
- dominios;
- recursos;
- servicios.

### En la práctica

- Asignar una **IP estática**.
- Actualizar desde el principio.
- Utilizar una contraseña fuerte.
- Activar/configurar el cortafuegos.
- Comprobar conectividad.
- Comprobar DNS.
- Verificar el acceso desde los clientes.
- Documentar toda la configuración.

> **Error frecuente:** pensar que un servidor recién instalado ya está preparado para producción.

> **Corrección:** después de instalar hay que **configurar, actualizar, asegurar, comprobar y documentar**.

# Resumen de la unidad

## Conceptos que deben quedar claros

1. **Planificación:** definir recursos, almacenamiento, nombre, red y función antes de instalar.
2. **Instalación:** conocer el proceso tanto en Windows Server como en Linux Server.
3. **Configuración inicial:** IP, DNS, nombre, hora, seguridad y actualizaciones.
4. **Comprobación:** verificar que el servidor funciona y es accesible desde los clientes.
5. **Automatización:** desatendida, clonación e instalación por red.
6. **Fichero de respuestas:** automatiza las decisiones que normalmente realiza el instalador.
7. **Actualizaciones:** deben planificarse y probarse antes de aplicarlas en producción.
8. **Administración:** personalizar el entorno para trabajar mejor, no para decorar.
9. **Documentación:** registrar la configuración y los cambios.
10. **Vía de vuelta:** disponer de copia o instantánea antes de cambios importantes.
